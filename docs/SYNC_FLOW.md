# BOSS 候选人同步与提醒流程

## 1. 点击候选人：查重并立即提醒

1. 扩展只在 BOSS `/web/chat/index` 沟通页启用；离开该页面立即清空并隐藏面板。
2. 招聘人员身份直接取 BOSS 页面右上角姓名；插件无需内部登录或内部令牌。首次成功发送时自动建立该页面身份。
3. 初次进入沟通页识别当前候选人后，同时发起查重和候选人同步；开发环境显示运行状态。
4. 招聘人员切换候选人后，候选人指纹变化只发起一次 `/plugin/context/check` 和一次幂等的 `/plugin/conversations/sync`。点击同步会创建/更新候选人飞书行（第一次看到就建行，会话时间变新就刷新 `更新时间`），但不会创建跟进关系、`MESSAGE_SENT` 事件或截图。
5. **停留在同一个候选人上时，会话本身的新动静会重新查重一次**：你在手机或另一个浏览器里回消息、或候选人回你，页面重渲染后会话时间变新 → 重新发起一次 `/plugin/context/check`（`sync_reason=CONVERSATION_UPDATED`）并幂等同步。这跟第 4 条不冲突：指纹没变的**重复重绘**不会重复查重（判据是同一个 `observedSyncKey`），只有会话时间/状态/岗位真的变了才算新事件。候选人发来消息、在线状态、未读数和纯 DOM 抖动都不重复创建记录；真实发送事件仍由独立的发送观察器登记。
6. 四项身份完全一致、同名同岗位或 BOSS 原生同事沟通记录命中时，页面立即提醒，并向**最近一次真实沟通该候选人的招聘者**发送一条飞书私聊。真实发送的消息（`sent_at`）一定计入“真实沟通”，只打开页面浏览不算；因此第二个真正发消息的招聘者会收到提醒，第一个沟通的人在当时无人可提醒。同一查看者、历史招聘者、候选人身份的相同探测默认 30 分钟内不重复发送（`LOOKUP_ALERT_COOLDOWN_MINUTES`），证据升级立即补发。

## 2. 招聘人员发送任意消息：登记真实沟通事件

1. 扩展先观察招聘人员的发送动作（发送按钮、Enter 或快捷语），再等待页面出现“送达/请求已发送”或已发文本且输入框清空的成功证据。只有成功后才调用 `/plugin/engagements/message-sent`。
2. 消息正文不上传、不记录、不进入飞书；仅传候选人、岗位、招聘人与发送时间，以及当前聊天区域可可靠识别的消息计数、最后消息时间和白名单动作类型。每次成功发送都会在 PostgreSQL 写入一条 `MESSAGE_SENT` 事件并刷新飞书行，但**发送永远不截图**（面试邀约也不截）：整段截取会滚动招聘者自己的会话面板，而发完消息后通常还在继续输入。截图只有一个来源——补扫（定时 23:30 / 手动"立即检查"/ 页面打开补扫，每个已读会话一张），加上某一行还没有可用截图时的一次补图。点击、巡检、列表监控和发消息都不截图。后台按招聘者、BOSS 账号和候选人聚合“主动沟通”次数；这个统计不依赖飞书表是否同步成功。
3. 同一发送事件使用 `client_event_id` 幂等，页面重试不会重复建事件。API 不可用时，扩展只持久化这些最小元数据并后台重试。

## 3. 数据库登记与比较

1. API 再次校验页面必须是 BOSS 沟通页。
2. BOSS 岗位原名就是有效业务字段，候选人和岗位页面直接展示沟通列表中的名称。标准岗位映射只是管理员需要统一报表口径时的可选归一化；尚未归一化时仍保存候选人、BOSS 岗位和发送事件，不阻断候选人、主动沟通或面试状态统计。
3. 候选人来源按“招聘人员 + 姓名/年龄/工作年限/学历身份签名 + 岗位”生成幂等标识。**同一招聘账号 + 同一候选人 + 同一岗位永远只有一行**：BOSS 的资料卡是分段渲染的，同一个人在两次扫描里可能读到不同的年龄/学历（例如一次只有 `26届`、另一次只有 `26年`），身份签名因此变化。出现这种情况时按“姓名 + 标准岗位”复用已有行，不新建第二行。判定谁能复用、谁该分开只看**年龄**这一个稳定事实（两边都有年龄且不同才视为不同人）；工作年限和学历只是佐证，不参与拆分，否则同一个人会因为渲染抖动被拆成两行。岗位名里混入的列表文本（`… 最近关注: … 25届 沟通的职位-… 送达 …`）会在参与身份计算前被剥离。另一招聘人员或另一岗位仍生成另一条来源记录。
4. `开始聊天时间` 取该招聘人对该候选人岗位的最早可验证沟通时间；`更新时间` **取招聘者发出的消息气泡时间**（会话里最后一条可验证外发消息的时刻），而不是左侧列表行的时间——列表时间在旧会话上会退化成 `09月05日` 这种没有时刻的标签。乱序重试只会保留较新的时间，不会缩小时间范围；补扫如果只拿到更粗的列表时间，也不会把已经记录的精确气泡时间改回去。
5. API 自动建立当前招聘人员的跟进关系，不要求点击“已跟进”等按钮。
6. API 在同公司其他招聘人员的来源记录中比较候选人：平台 ID 一致为确认重复；姓名与标准岗位一致为疑似重复；姓名与岗位类别一致或仅姓名一致作为较弱历史证据。

## 4. 飞书候选人表同步

1. 每个“BOSS 账号 + 候选人四要素身份 + 岗位”对应飞书一条系统记录。业务列包含候选人、BOSS 账号、飞书账号、BOSS 岗位、开始聊天时间、更新时间、状态和聊天框截图。更换飞书负责人只更新当前分配，候选人、附件、记录 ID 和同步历史继续归属于原 BOSS 账号。年龄、工作年限、学历用于严格查重；身份签名、会话岗位标识和系统记录标识保留在服务端。
2. API 与业务写入同一事务创建/合并 `CandidateSyncOutbox`，立即返回；专用 Worker 异步写飞书，失败指数退避并最多重试 5 次。**进入飞书队列的情况**：点击/补扫第一次看到该候选人（建行）、这次读到的会话时间比已存时间更新（刷新 `更新时间`）、已有来源但从未写成功过，以及招聘者真实发消息的 `MESSAGE_SENT`。反过来，时间没变的重复“点开看看”只更新内部索引，不会重复写飞书；点击永远不创建跟进关系、招聘事件或 `MESSAGE_SENT`，也不截图。
3. 飞书以候选人标识幂等更新：已缓存 `feishu_record_id` 时直接更新；首次同步会翻页搜索全表，不受 500 条单页限制。已存在则更新，不存在则新建。
4. 因为候选人标识包含招聘人员作用域，同一候选人由另一招聘人员跟进时会新建另一行，不会合并到原招聘人员的行。

后台“全公司候选人”和招聘者工作台直接读取 PostgreSQL 的候选人来源、招聘事件和面试记录，不需要先写入飞书表。飞书表是共享汇总/附件出口；即使飞书同步排队或失败，后台仍可查看候选人、岗位和主动沟通次数。

### 点击实时查重

点击候选人时，扩展上传姓名、年龄、工作年限和学历。四项完整且规范化值全部一致时作为确认重复；姓名和岗位一致时作为疑似重复，即使四项不完整也可以疑似提醒。API 排除当前招聘者和人工行。飞书不可用时明确返回“查重暂不可用”，不伪装成无历史。

若页面已展示 BOSS 原生“同事沟通”记录，扩展同时采集其中的招聘者、岗位和沟通时间。该记录由 BOSS 自身确认候选人身份，因此优先级高于四项身份兜底：与飞书“招聘者 + 岗位”系统行一致时，用飞书状态和更新时间补全；飞书无对应行时仍提示“BOSS 已确认、飞书未同步”。当前招聘者自己的记录会被排除。原生记录会触发页面和私聊提醒；查重调用本身是只读的，不创建候选人来源、跟进、招聘事件、正式冲突、飞书行或截图（同一时刻的 `/plugin/conversations/sync` 才会按上面的规则建/更新飞书行）。

扩展不会自动点击“沟通记录”，避免弹窗打断招聘操作。BOSS 未打开弹窗时并不向页面提供同事记录，因此日常点击候选人仍由飞书四项精确匹配在后台完成；招聘者手动打开原生记录时，扩展会被动读取并立即增强本次查重。扩展不调用未授权的 BOSS 内部接口，也不依赖未经现场确认的 class 选择器。

### 其他端回复：只读列表监控（实时查重）

招聘者在手机或另一台电脑上回复后，**本机标签页不会为那一行会话产生任何事件**：页面观察器只对"当前打开的候选人"重新查重，那一行属于别人。补扫又固定在 23:30，所以旧行为下必须手动"立即检查"或重新加载页面才会处理它。为此扩展对沟通列表做**只读监控**：

- **触发**：每 15 秒一次，以及标签页重新可见时立即一次。读取 BOSS 已挂载的列表行文本时间，与这台设备记录的"上次看到的该行时间"比较（`boss-list-watch:<BOSS账号>`，只存"行标识 → 活动时间"）。只有该行时间变新才处理，时间没动不产生请求。
- **只查重，不同步**：对变新的行只调用一次 `/plugin/context/check`，身份只用列表行能给出的候选人姓名 + BOSS 岗位（年龄、学历留空，因此最多"疑似重复"级别）。**不点击、不切筛选、不滚动、不同步**：不创建候选人来源、不写飞书行、不截图、不产生 `MESSAGE_SENT` 事件，也不调用 `GET /plugin/conversations/index`。已读和未读行都只读不点，所以不会替招聘者把红点清掉。
- **和补扫各管一段**：当前打开的候选人由它自己的完整查重负责（含年龄、学历、BOSS 原生同事记录），列表监控跳过该行，避免用弱证据覆盖已确认的卡片。
- **冷启动不刷屏**：第一次看到某一行只记录、不查重，因此安装后不会对列表里每个会话各发一次请求。频率上限为每轮最多 5 行，失败或服务端返回 `IGNORED_PAGE` 时不推进水位、下一轮重试。
- **提醒语义**：列表监控传 `sync_reason=LIST_ACTIVITY_DETECTED`，走服务端正常冷却（`LOOKUP_ALERT_COOLDOWN_MINUTES`）；只有真实的未读→已读才用 `UNREAD_CANDIDATE_OPENED` 绕过冷却。页面卡片会标注“沟通列表检测到新动态”，避免被误认成当前打开候选人的提醒。
- **不打扰页面**：只读取当前筛选下**已挂载**的行，绝不点击、不切筛选（不会替招聘者切到"沟通中"）、不滚动、不改动页面焦点；页面上唯一的可见变化是命中重复时右下角的提醒卡片。
- **开关**：与“自动补扫当前候选人列表”同一个开关；关闭后监控一起停止。
- **覆盖范围**：因为不切筛选也不滚动，当前筛选之外、或未挂载（视口外）的会话不会被监控，这些仍由点击、补扫或"立即检查"负责。

### 隔夜补扫和快照

扩展设置页提供“自动补扫当前候选人列表”开关，默认开启，在“沟通中”列表周期巡检。**巡检只读，不再点开任何未读会话**——打开会话正是 BOSS 判定“已读”的动作，旧实现逐行点开会把招聘者的红点全部清掉，等于替他把消息读了。现在的规则：

- **未读行一律不碰**：不点击、不同步、不建索引。招聘者自己去读，读的那一次访问才是它的同步时机。
- **每天一轮，锚点 23:30；补扫本身带水位锚点，不会每次全扫**：全量补扫固定在**每天 23:30（北京时间）**跑一轮，也就是"今天 23:30 → 明天 23:30"算一个工作日周期——23:30 之后还在聊的候选人，归到当前这个周期，不会被已经关闭的窗口漏掉。如果那一刻浏览器没开，下一次打开沟通页时会自动补一轮全量补扫（而不是干等到第二天 23:30）：扩展在本地为每个 BOSS 账号记录"最近一次成功补扫时间"，只要当前时间已经越过最新一个 23:30、而那个窗口没有成功补扫记录，本次打开就按全量模式跑。**这个自动补扫不会在你干活时抢页面**：打开页面后需要连续 60 秒没有任何按键/点击/滚动、并且焦点不在输入框，才会开始；你一直在用，它就每 30 秒看一次、一直等着，永远不会在你打字或读会话时切筛选、点会话。到点的定时轮和手动"立即检查"仍按原节奏立即开始。一小时内的重复打开不会重复补，避免反复刷新时重复重活；手动"立即检查"同样计入当天已完成。
- **补扫范围 = 今天这个周期内有动静的会话**："今天"按 23:30 → 次日 23:30 计算（见上一条）。一轮补扫从**当前周期的起点**开始读列表，叠加**同步锚点**——上一轮成功补扫已经覆盖到的最新会话时间——只打开"比这两个里更晚"的会话，遇到不新于锚点的行就停。所以：
  - 老会话只要今天没有新动静，就**不会**被重新打开、重新截图（不再每次全扫整个沟通中列表）；
  - 出差几天回来也不会去追多天积压，只补**今天**这一段；
  - 页面打开触发的自动补扫与定时/手动补扫**用完全相同的范围**（今天的会话），没有"前 N 条"这类额外截断；一轮的规模=今天真正有动静的会话数。
- **截图只在补扫里统一产生**：定时/手动/页面打开的补扫（每个已读会话一张），加上某一行还没有可用截图时的一次补图。点击候选人、巡检刷新时间、列表监控和发消息（含面试邀约）都**不截图**，所以不会出现"截图一直有"、也不会在招聘者打字时抢面板。
- **收尾一定回到你自己的列表**：补扫必须先把列表切到"沟通中"才能逐行对账，所以开始前先记住你当时在读的筛选，结束时还原；还原是**验证过**的——点一次没生效会重新定位再点一次。如果那个筛选当时认不出来，就回到**"新招呼"**，绝不会把你停在工具自己选的"沟通中"上（那会让你以为列表"不动了"）。筛选标签带数字角标（`新招呼 3`）、CSS-module 哈希类名（`tabItem_active__x`）、以及标记挂在外层或嵌套节点上的情况都能识别；`inactive` 这类词不会被误判成选中。同一个标签渲染了多个节点时，按"其中任意一个是选中态"判断，不被陈旧节点挡住。

### 实时提醒通道

`GET /plugin/stream` 是每台扩展一条的服务端推送（SSE）长连接：命中一旦写入提醒记录，就立刻推给该公司的在线设备；页面已经停留在该候选人上时也能立即弹出重复提醒，不必等下一次页面观察或补扫。

该通道只传递提醒标识和业务标签（候选人姓名、岗位、命中招聘者、匹配依据、时间），不传聊天内容、Cookie 或附件。它是**加速器而不是事实来源**：推送丢失、连接断开或扩展离线都不影响结果，权威记录仍是 PostgreSQL 提醒行和飞书私聊，下一次页面检查会从表里重新判定；扩展按指数退避静默重连，从不因推送失败打断招聘操作。
