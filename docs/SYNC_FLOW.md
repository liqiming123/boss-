# BOSS 候选人同步与提醒流程

## 1. 点击候选人：查重并立即提醒

1. 扩展只在 BOSS `/web/chat/index` 沟通页启用；离开该页面立即清空并隐藏面板。
2. 招聘人员身份直接取 BOSS 页面右上角姓名；插件无需内部登录或内部令牌。首次成功发送时自动建立该页面身份。
3. 初次进入沟通页只记录当前候选人指纹，不请求 API，不写数据。开发环境显示运行状态。
4. 招聘人员切换候选人后，候选人指纹变化只发起一次 `/plugin/context/check`。该接口不创建候选人来源、跟进、招聘事件、正式冲突或候选人飞书行；命中规则时只创建最小化查重提醒状态和通知 Outbox。
5. 候选人发来消息、在线状态、未读数和其他 DOM 变化不创建记录。
6. 四项身份完全一致、同名同岗位或 BOSS 原生同事沟通记录命中时，页面立即提醒并向当前查看者和历史招聘者发送飞书私聊。同一查看者、历史招聘者、候选人身份和岗位 24 小时内不重复发送；证据升级立即补发。

## 2. 招聘人员发送任意消息：才登记

1. 扩展先观察招聘人员的发送动作（发送按钮、Enter 或快捷语），再等待页面出现“送达/请求已发送”或已发文本且输入框清空的成功证据。只有成功后才调用 `/plugin/engagements/message-sent`。
2. 消息正文不上传、不记录、不进入飞书；仅传候选人、岗位、招聘人与发送时间，以及当前聊天区域可可靠识别的消息计数、最后消息时间和白名单动作类型。
3. 同一发送事件使用 `client_event_id` 幂等，页面重试不会重复建事件。API 不可用时，扩展只持久化这些最小元数据并后台重试。

## 3. 数据库登记与比较

1. API 再次校验页面必须是 BOSS 沟通页。
2. BOSS 岗位优先映射到标准岗位。尚未映射时仍保存候选人、BOSS 岗位和发送事件，标准岗位暂留空，同时登记待映射岗位。
3. 候选人来源按“招聘人员 + 姓名/年龄/工作年限/学历身份签名 + 岗位”生成幂等标识。同一招聘人员再次扫描同一候选人岗位时更新原记录；另一招聘人员或另一岗位生成另一条来源记录。
4. `开始聊天时间` 取该招聘人对该候选人岗位的最早可验证沟通时间，`更新时间` 取最新可见互动时间；乱序重试不会缩小时间范围。
5. API 自动建立当前招聘人员的跟进关系，不要求点击“已跟进”等按钮。
6. API 在同公司其他招聘人员的来源记录中比较候选人：平台 ID 一致为确认重复；姓名与标准岗位一致为疑似重复；姓名与岗位类别一致或仅姓名一致作为较弱历史证据。

## 4. 飞书候选人表同步

1. 每个“招聘者 + 候选人四要素身份 + 岗位”对应飞书一条系统记录。招聘人员主要查看的业务列是：候选人、当前招聘者、BOSS 岗位、开始聊天时间、更新时间、状态和聊天框截图。年龄、工作年限、学历用于严格查重；身份签名、会话岗位标识和系统记录标识是幂等与查重必需的技术列，建议在飞书的日常使用视图中隐藏。
2. API 与业务写入同一事务创建/合并 `CandidateSyncOutbox`，立即返回；专用 Worker 异步写飞书，失败指数退避并最多重试 5 次。
3. 飞书以候选人标识幂等更新：已缓存 `feishu_record_id` 时直接更新；首次同步会翻页搜索全表，不受 500 条单页限制。已存在则更新，不存在则新建。
4. 因为候选人标识包含招聘人员作用域，同一候选人由另一招聘人员跟进时会新建另一行，不会合并到原招聘人员的行。

### 点击实时查重

点击候选人时，扩展上传姓名、年龄、工作年限和学历。四项完整且规范化值全部一致时作为确认重复；姓名和岗位一致时作为疑似重复，即使四项不完整也可以疑似提醒。API 排除当前招聘者和人工行。飞书不可用时明确返回“查重暂不可用”，不伪装成无历史。

若页面已展示 BOSS 原生“同事沟通”记录，扩展同时采集其中的招聘者、岗位和沟通时间。该记录由 BOSS 自身确认候选人身份，因此优先级高于四项身份兜底：与飞书“招聘者 + 岗位”系统行一致时，用飞书状态和更新时间补全；飞书无对应行时仍提示“BOSS 已确认、飞书未同步”。当前招聘者自己的记录会被排除。原生记录会触发页面和私聊提醒，但点击阶段仍不创建候选人来源、跟进、招聘事件、正式冲突、候选人飞书行或截图。

扩展不会自动点击“沟通记录”，避免弹窗打断招聘操作。BOSS 未打开弹窗时并不向页面提供同事记录，因此日常点击候选人仍由飞书四项精确匹配在后台完成；招聘者手动打开原生记录时，扩展会被动读取并立即增强本次查重。扩展不调用未授权的 BOSS 内部接口，也不依赖未经现场确认的 class 选择器。

### 隔夜补扫和快照

扩展设置页提供“自动补扫当前候选人列表”开关，默认开启。开启后按招聘账号读取上次成功网页沟通时间，首次回看 48 小时；候选人列表结构通过严格几何与内容校验后才自动逐项打开，点击、键盘或滚轮操作会暂停 30 秒。只有能确认招聘者曾发出消息的会话才创建记录。同步成功后推进水位；关闭开关不会删除水位。聊天区域长图默认自动上传和重试，API 只保存飞书附件令牌，不保存图片二进制。

系统只根据当前聊天区域内已确认发送的 BOSS 标记同步“已获取简历”等流程状态；左侧列表、快捷按钮和资料文本不会参与状态判定。员工明确点击当前聊天区域的预览/查看附件后，扩展优先下载原始附件并同步到飞书；如果页面只有预览而没有可下载地址，则截取预览区域作为图片同步。服务端只保留飞书附件令牌、哈希、文件名和状态。

状态规则 `boss-status-v3` 会在当前会话存在可靠外发证据且没有拒绝证据时，修复旧版规则造成的“待约面/已拒绝”误判；不会批量修改未重新核验的历史行。聊天快照失败会写入 `FAILED`，用户操作中断写入 `INTERRUPTED`，均不阻断候选人记录同步。

## 5. 页面和飞书通知

1. 没有其他招聘人员记录：正式环境页面静默；开发环境显示“招聘消息已登记；未发现其他同事跟进”。
2. 找到其他招聘人员记录：当前招聘人员对应的飞书记录新增或更新，`提醒` 写入命中的招聘人员及内部跟进阶段；页面显示重复提醒。
3. 扩展弹窗可发起飞书 OAuth，将当前飞书个人身份绑定到 BOSS 右上角姓名。服务端只保存 `open_id`、`user_id` 和飞书昵称，不保存个人访问令牌。
4. 解绑同样经过飞书 OAuth，只有当前已绑定的同一个飞书用户才能解绑；解绑后取消尚未发送的私聊任务，不影响 BOSS 页面提醒和候选人表同步。
5. 点击阶段对四项完全一致、BOSS 原生同事沟通确认或“同名 + 同岗位”的疑似重复立即页面提醒并创建双方私聊；发送或补扫确认历史外发后，再建立正式幂等冲突和候选人业务记录。
6. 同一冲突和同一接收人只产生一条幂等私聊通知。
