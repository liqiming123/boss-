# 架构决策

- 候选人来源独立保存；姓名和岗位永不触发永久合并。
- 点击候选人和自动补扫共用同一条实时同步路径：表格里没有就建行，这次读到的会话时间比已存时间新就刷新 `更新时间`；时间没变的重复查看不重复写飞书。点击不创建虚假的跟进关系或 `MESSAGE_SENT` 事件，也不截图。命中四项确认、同名同岗位疑似或 BOSS 原生确认时，允许写入最小化提醒冷却状态和通知 Outbox，并私聊“最近一次真实沟通该候选人”的招聘者：确认发送的消息（`sent_at`）一定计入真实沟通，仅浏览不算；卡片只列其他招聘者，从不列收件人自己。只有招聘人员成功发送真实消息才登记业务跟进事件和正式冲突。
- 聊天长图只在补扫里采集：定时/手动的历史补扫（每个已读会话一张），加上某一行还没有可用截图时的一次补图。**消息发送永远不截图，面试邀约也不截**——整段截取要滚动招聘者自己的会话面板，邀约通常发生在会话中途、后面还要继续输入，成本和打扰都高于收益；邀约本身照常登记 `MESSAGE_SENT`、面试安排和 `已约面` 状态。
- 同一点击提醒默认 30 分钟内不重复发送（`LOOKUP_ALERT_COOLDOWN_MINUTES`）；证据升级立即补发。
- 其他端回复的实时性只做到“查重”为止：扩展对沟通列表做只读监控（每 15 秒 + 标签页重新可见时），只读取已挂载行的活动时间，与设备本地的行水位比较，对变新的行只发一次 `/plugin/context/check`，身份仅取列表行的姓名 + 岗位。它不点击、不切筛选、不滚动、不同步，所以不创建候选人来源、不写飞书行、不截图、不产生 `MESSAGE_SENT`，也不查服务端会话索引；当前打开的候选人仍由自己的完整查重负责，列表监控跳过该行。
- 当前打开的会话由页面观察器负责重查：指纹没变但会话时间/状态/岗位变了（你在手机回消息、候选人回你）就算一次新事件，重新查重一次（`CONVERSATION_UPDATED`）；纯重绘不算。判据与同步去重共用同一个 `observedSyncKey`，所以“同一个会话发生了新事情”只有一个定义。
- 候选人飞书记录固定为“招聘者 + 候选人 + 岗位”一行，平台候选人 ID 也不能跨岗位合并。
- 招聘状态只随明确且更强的证据前进；缺失证据和默认“沟通中”不回退已有状态，已拒绝与已入职为终态。
- `conversation_started_at/conversation_updated_at` 分别是 BOSS 会话中可验证的最早/最新互动时间；`first_seen_at/last_seen_at` 仅是内部处理时间。补扫比较最新会话时间，旧观测不会覆盖新记录。
- 候选人飞书表同步使用事务 Outbox 与专用 Worker，不阻塞消息登记 API。
- PostgreSQL 是唯一核心存储；通知使用事务 Outbox，不引入消息队列。
- 插件仅提取最小字段并通过 API 工作，不读取 Cookie、不拦截请求、不上传 HTML。
- BOSS 选择器无现场证据时保持空配置，避免把猜测当成适配结果。
